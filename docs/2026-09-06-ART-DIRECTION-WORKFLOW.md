# 2026-09-06：视觉探索、分阶段交付与视觉提升

本轮实施已讨论的优先项 1、2、4，范围为设计、细调和两者共享流程。不修改 Compose/Flutter 实现 Skill，不改变现有 Schema 1.1、像素比较阈值或交付验证器的验收规则。

## 发生了什么变化

1. **从参考到画面**：参考必须实际看过；记录可见处理、产品适用原因、迁移边界及它在新图中的位置。方向不明确时通常比较两个同内容方案，已有方向则继承。对真实渲染结果提出修改并重新看图。
2. **按阶段完成**：探索稿不再被完整问卷、组件目录和 schema-complete JSON 阻塞。确认稿保留选定/代选证据及关键适配，开发交付继续执行完整的约定范围内验收。用户要求完整设计时不能停在探索阶段。
3. **细调支持视觉提升**：明确区分审计、纠错、视觉提升与回归。层级或构图提升无需虚构 Material 违规；已授权的改进可以执行，冻结品牌与业务边界仍保留。
4. **中文主导排版**：中文产品先评估中文界面字体，并在实际页面里配合英文、数字和图标检查。没有强制所有项目换字体或图标家族。
5. **避免虚假验证**：实际截图、定性判断、用户选择、自动化检查各自注明证据边界；不得制造差的旧稿来展示提升。

## 产品同学如何调用

探索：

```text
使用 $material-android-ui-design。
读取这个原型，沿用已提供的主题色和 Logo。
先给我两种有实质区别的真实页面方向，说明参考如何落实到画面。
我选完再展开完整设计。
```

授权推进：

```text
使用 $material-android-ui-design。
主题色和 Logo 沿用；其余按推荐方案。
先验证代表页，你可以代选方向，然后完成约定范围的设计交付。
```

视觉提升：

```text
使用 $material-android-ui-refine。
改善这个页面的层级和堆砌感，允许调整构图、分组和排版。
保持 Logo、主题色、业务动作和页面范围。
给出真实修改前后图，说明观察、修改和结果。
```

局部修复或只读审计仍按原意处理，无需新建完整交付契约。

## 验证边界

- 仓库回归：39 项 Python 测试、9 项 JavaScript 测试通过；契约示例通过草稿校验；两个 Skill 的结构校验通过。未改动的交付校验器仍拒绝将不完整草稿当作完整交付。
- Tuntas 页面演练：已使用当前试驾业务原型完成通话准备、客户档案、通话中三张试稿及两种入口方向；真实截图驱动了一轮构图细调，并发现、修复了预览的正文/标签缩放问题。
- 样例检查包括 360×800、320×720 的 150% 字号、一个深色样例和 840×800 双栏档案，以及字幕展开、静音演示状态、依据与结束提示。仅说明这些浏览器演练检查，不冒充原生设备或完整 Figma 验收。
- 原型、首稿、最终稿、PNG 与测量报告独立保存在工作区 `artifacts/2026-09-06-art-direction/`，没有写入或覆盖已有产品 Figma，也没有加入 Skill 发布包。
- 这是作者试跑，尚不是独立前向测试；原型与新概念不能被称为受控的新旧 Skill 实验。A/B 是同内容构图候选，不是模型能力对比。
- 审美提升仍需查看真实产出与产品反馈；不以测试通过或模型升级宣称已经有更好的审美。
